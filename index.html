    流程
    
    
    兩條線：事先建索引，查詢時才檢索
    
    
    建索引在離線完成一次，之後每個問題只走查詢那條線。虛線框是進階做法，上面的示範可以切換其中幾個。向量化時，問題與文件必須用同一個 embedding 模型，向量才能比較。
    
  
    
  
    
  
    
  
    RAG 不改模型權重。知識放在索引裡，更新資料只要重建或增補索引，回答也能附上來源編號，方便查核。
    

    


    
  
    
    
    切塊
    
    
    片段切多大，決定檢索找得到什麼
    
    
    切太小，一句話可能失去主詞；切太大，無關內容會稀釋相似度，也佔掉提示長度。重疊可以避免關鍵句被切斷，但會增加片段數。
    
  
    
  
    
  
    
    
    
      
    
      
    
      
    
        
    0片段數
    
        
    0總字數（含重疊）
    
        
    0%重複比例
    
        
    0切在句子中間
    
      
    
      
    上圖每一列是一個片段，橫軸是原文位置：黃色是與前一片段重疊的部分，虛線是句號位置，紅點表示片段在句子中間被切斷。真實系統常以 token 計長度，並優先在句號、段落處切開。
    
    
    
    
    
  
    

    


    
  
    
    
    向量化
    
    
    文字怎麼變成可以比較的向量
    
    
    每段文字被轉成一串數字。兩個向量夾角越小，餘弦相似度越接近 1，代表內容越相近。本頁用的是字元二元組的 TF-IDF 稀疏向量：字面重疊越多、越少見的詞組權重越高。實務上多用神經網路的密集 embedding，它能把「禁忌」和「過敏」這種沒有共同字的詞也放得很近。
    
  
    
  
    
  
    
    
    
      
    輸入兩個句子，即時計算相似度
    
      
      
      
    0　餘弦相似度（0 到 1）
    
      
    
      
    右圖列出兩句的二元組與權重，黃色是兩句共有、真正貢獻相似度的部分。試著把句子 B 改成「我不能吃花生」，看相似度怎麼掉。
    
    
    
    
    
  
    
  
    資料庫裡 11 則記憶彼此有多像
    顏色越深越相似。m4 與 m5 都在講日文課，m1、m6、m10 都提到旅行；這些相近的片段會在檢索時互相競爭名次。滑鼠停在格子上可看數值。
    
  
    

    


    
  
    
    
    檢索方法
    
    
    同一個問題，三種排名方式
    
    
    BM25 是傳統關鍵字檢索，看詞組出現次數與稀有程度；字元 TF-IDF 餘弦是上方示範用的方法；RRF（倒數排名融合）把兩份排名合併，每份名次 r 貢獻 1/(60＋r)。兩種方法都只看字面，所以沒有共同字的同義詞仍會漏檢，這是密集 embedding 要補的部分。下圖跟著上方示範的問題與「查詢改寫」設定即時更新，綠線是這題真正需要的證據。
    
  
    
  
    
  
    
    
    
      
    重排序：讓較新的證據往前
    
      
    取相似度前 6 名，用示範公式「新分數＝相似度×(1＋0.6×新近度)」重新排序，新近度依日期從 0 到 1。綠線代表名次上升，紅線代表下降。實務上的重排序多半用 cross-encoder 模型逐對打分，這裡只示範時間這一個因素。
    
      
    
    
    
    
    
      
    向量索引怎麼快速找到近鄰（HNSW 示意）
    
      
    百萬筆向量不能逐一比較。HNSW 把節點分層：上層少而稀疏，可以大步跳；越往下越密。搜尋從頂層入口出發，每層貪婪地走向離問題（★）最近的節點，再往下一層細找。
    
      
    
    
    
  
    

    


    
  
    
    
    演進
    
    
    從單次檢索到會修訂的代理記憶
    
  
    
  
    
  
    
    
    
      
    做法核心想法何時檢索資料更新時主要風險
    
      
        
    Naive RAGLewis et al., 2020切塊、向量檢索、塞進提示每題一次重建或增補索引漏檢、片段缺上下文
    
        
    Advanced RAG混合檢索（BM25＋向量）、查詢改寫、重排序每題一次，前後多處理同上多一道模型呼叫的延遲與成本
    
        
    Self-RAGAsai et al., 2023模型自己判斷要不要檢索、片段有沒有用按需同上需要特別訓練的模型
    
        
    GraphRAGEdge et al., 2024先抽實體與關係建圖，做社群摘要回答全域問題每題，走圖與摘要建圖成本高，增量更新困難建庫大量呼叫模型
    
        
    Agentic RAG代理規劃多輪查詢、呼叫工具、合併結果多輪、自主決定同上步數與成本難以預測
    
        
    Agent Memory如 Mem0、A-Mem邊對話邊寫入記憶，處理更正、撤回與遺忘每輪對話記憶本身要能修訂與追溯舊記憶沒失效，回答引用過期證據
    
          
    
    
  
    
  
    上方示範用的正是代理記憶型資料：小林改過住宿和上課時間。沒有時間感知時，檢索會同時拿到新舊兩條，模型無從判斷該信哪一條。
    

    


    
  
    
    
    AGENT MEMORY
    
    
    代理記憶：一邊對話一邊被改寫的資料庫
    
    
    一般 RAG 的文件由人維護，內容相對固定。代理記憶的資料由對話即時寫入，使用者會更正、撤回、重複確認，同一件事會有多個版本。所以除了怎麼檢索，還要決定怎麼寫入、怎麼更新，以及回答之後記憶又變了該怎麼辦。
    
  
    
  
    
  
    每一輪對話先抽出候選事實，再和既有記憶比對，決定新增、更新、撤回或不變。Mem0 等系統用的就是這類操作；差別在於舊版本要不要保留、能不能追溯。
    

  
    
    
    記憶的四種類型
    借用認知科學的分類。情節記憶記錄「什麼時候發生了什麼」，反覆出現的內容再整合成語意記憶；做事的偏好與規則則形成程序記憶。工作記憶就是目前的上下文視窗，容量有限，所以其他三種要存在外部、需要時再檢索。
    
    
    
  
    

  
    逐輪模擬：小林的 12 輪對話
    拖動滑桿或按「下一輪」，看每句話觸發哪種操作。泳道圖每一列是一項記憶，藍色是目前有效的版本，灰色是已被取代的舊版本，紅色是被撤回的，綠點表示使用者再次確認。
    
  
    
    
    
      
      
      
      
      
    
    
    
    
  
    
  
    
  
    
    
    此刻去問代理
    答案只依截至這一輪的有效記憶。往回拖動滑桿，就能看到「當時」代理會怎麼回答。
    
    
    記憶數量怎麼成長
    原始訊息每輪都增加；整合後的有效記憶成長較慢，更新與撤回不會讓它變多。版本總數則保留了變更歷史。
    
  
    

  
    三種寫入策略，同一段對話
    跟著上方滑桿變化。比較住宿（被更新過）、健身（被撤回）、咖啡（被修正）三項在不同策略下留下什麼。
    
  
    

  
    支持關係：撤回一則證據，哪些記憶要跟著失效？
    推導出的記憶要記住自己靠哪些證據成立。「或」表示任一組支持就成立，「且」表示全部都要成立。點左邊的證據把它撤回，看影響怎麼傳遞。這個想法源自真值維護系統（TMS）。
    
  
    
    
    
    
    目前的推理
      
  
      

  
      回答之後，記憶又變了
      代理的回答可能被快取或延後送出。如果中間有新的寫入，要在新的記憶快照上重新檢索，確認交付的證據完全相同才能沿用舊回答。
      
  
      

      


      
  
      
    
      失敗模式
      
    
      RAG 常見的四種錯，都能在上面重現
      
  
      
  
      
    
      漏檢
      問題用語和資料不同，「飲食禁忌」比對不到「花生過敏」。查詢改寫或混合檢索可以補救。
      
    
      片段缺上下文
      一問一答被切成兩則：只取到「是的，下週開始」就不知道主詞，只取到問句又沒有答案。鄰近擴充把同一段對話一起帶入。
      
    
      新舊證據衝突
      京都與大阪兩條都被檢索到，模型可能挑錯。需要版本與時間資訊，或在寫入時讓舊記憶失效。
      
    
      相對時間沒換算
      證據寫「下週」，回答若照抄就失去意義。要用對話日期換算成實際日期。
      
  
      
  
      
    
      錯誤歸因：問題出在檢索還是生成？
      橫軸看該拿的證據是否全部交付，縱軸看回答是否正確。藍點是上方示範目前的位置。先判斷落在哪一格，才知道該調檢索還是調提示與生成。

      答案正確率
      和標準答案比對，如 F1 或完全相符。
      
    
      忠實度
      回答的每個主張，是否都能在交付的片段中找到。
      
    
      引用支持
      標註的引用編號是否真的支持那句話；用 LLM 自動評審時，需要先和人工標註校準。
      
    
      成本與延遲
      建索引、查詢、生成各花多少 token 與時間，要分開計算。
